# Claim and correction ledger

## Migration from v2 to v3

Historical v2 to v3 review conducted 2026-09-27. This table identifies significant claims in the historical `docs/knowledge` v2, their revised treatment, and primary evidence. The short descriptions in the “v2 claim” column paraphrase the claims for identification; they are not verbatim quotes and do not replace the full context. The source canon remains untouched. The audit provided in the conversation was treated as a set of hypotheses: each protocol-dependent claim was rechecked against a primary source.

| ID | v2 claim and location | Verification outcome / v3 wording | Evidence |
| --- | --- | --- | --- |
| C01 | `MCP-SERVER-BIBLE`: add sampling as a capability when the client supports it | Core sampling is deprecated in MCP 2026-07-28. A new implementation checks the protocol revision and client support; it does not depend on this capability. | [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28), [change summary](https://blog.modelcontextprotocol.io/posts/2026-07-28/) |
| C02 | `MCP-SERVER-BIBLE`: persistent sessions and server-side callbacks describe new MCP | Revision 2026-07-28 has a stateless core, without `initialize` or `Mcp-Session-Id`; interactions requiring a user have new semantics. An application may still maintain its own explicit state. | [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28), [change summary](https://blog.modelcontextprotocol.io/posts/2026-07-28/) |
| C03 | `MCP-SERVER-BIBLE`: “Streamable HTTP (SSE)” names one transport | Streamable HTTP and the older HTTP+SSE belong to different protocol generations; an implementation checks the client's revision. | [MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports), [change summary](https://blog.modelcontextprotocol.io/posts/2026-07-28/) |
| C04 | `MCP-SERVER-BIBLE`: tool names require a prefix and tools can be registered only at startup | Names must be unique within one server; an aggregator can resolve collisions. The tool list may change. | [MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) |
| C05 | `MCP-SERVER-BIBLE`: one mandatory `success/data/hints` envelope and a ban on base64 | These are application conventions, not MCP requirements. The protocol provides `content`, `structuredContent`, and schemas, and allows base64-encoded images and audio. | C06 | `MCP-SERVER-BIBLE`: Python, PostgreSQL, Alembic, hexagonal architecture, and one server per domain are mandatory | The specification requires none of these. | C07 | `README`, `DEPLOYMENT`, `CONTEXT-ENGINEERING`: Code Mode is required with 10 or more servers | There is no universal threshold. | C08 | `AGENT-TEAMS`, `MCP-SERVER-BIBLE`, `README`: references are required above 5 KB; 4–7 tools or 15+ tools are hard thresholds | References and a smaller tool set can help, but thresholds depend on the model, format, and task. In v3, these are measured design decisions, not universal rules. | [OpenAI Tool Search](https://developers.openai.com/api/docs/guides/tools-tool-search), [OpenAI Skills](https://developers.openai.com/api/docs/guides/tools-skills) |
| C09 | `DEPLOYMENT`: the Responses API is a common gateway format across providers | Responses is an OpenAI API. Anthropic has Messages and Google has its own APIs; a multi-provider adapter needs capability mapping and semantic tests. | [OpenAI Responses](https://developers.openai.com/api/docs/guides/migrate-to-responses), [Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create), [Google Interactions](https://ai.google.dev/gemini-api/docs/interactions-overview) |
| C10 | `DEPLOYMENT`: one shared table of `reasoning_effort` and `budget_tokens` settings | Parameters depend on provider, model, and version: for example, OpenAI `reasoning.effort`, Gemini 3 `thinkingLevel`, and Gemini 2.5 `thinkingBudget`. Do not maintain them as one universal table. | [OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning), [Gemini thinking](https://ai.google.dev/gemini-api/docs/generate-content/thinking) |
| C11 | `DEPLOYMENT`, `PRODUCTION`: “the last message must be from the user” is an Anthropic/Gemini API rule | This is not a shared provider rule. | C12 | `DEPLOYMENT`: `stdio` is only for desktop applications | `stdio` can also run in an isolated service environment; the process and credential boundary is what matters. | [OpenAI MCP connections](https://developers.openai.com/api/docs/guides/agents-api/tools/mcp), [MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) |

| C16 | `SECURITY`, `HUMAN-IN-THE-LOOP`: every external action or write always needs fresh consent, while reads are safe | Approval depends on the effect, the scope of prior authorization, and policy. High-risk actions need an independent gate. | [OWASP GenAI Top 10 2026](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/), [OpenAI Human in the loop](https://openai.github.io/openai-agents-python/human_in_the_loop/) |
| C17 | `HUMAN-IN-THE-LOOP`: a tool's name or schema is enough to decide on approval; a dry run replaces consent | Policy must account for actual arguments, the target object, recipient, identity, and effect. | C18 | `MCP-SERVER-BIBLE`, `PRIMITIVES`: a model-supplied `tenant_id` argument and a `tenant_id` column in every table form a universal isolation pattern | Such a field may be useful data, but it is neither proof of authorization nor the only storage model. | C19 | `PRIMITIVES`, `EVENTS`: event sourcing and no hard deletion are general rules | A durable event log can aid audit and recovery, but is not required for every system. | C20 | `OVERVIEW`, `DEPLOYMENT`: four layers, a central gateway, and a separate service for each subagent are default requirements | These are architectural options. **Assessment of the supplied audit:** Its report of an HTTP 400 error for a final `assistant` message is correct for Claude 4.6+ and Mythos Preview, but not for all earlier models; see C11. Other claims about changes to MCP, providers, and A2A were carried forward only after checking the relevant specification. Calling the existing “design doctrine current” is too broad: many v2 recommendations are useful **options**, not standards for every project.
